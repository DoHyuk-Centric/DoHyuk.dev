# Git 브랜치 전략

## 기본 브랜치

- **`develop`**: 기본 브랜치. 모든 작업 브랜치는 여기서 분기한다
- **`main`**: 릴리스(실제 배포) 브랜치. `deploy.yml`이 `main` push를 트리거로 EC2에 자동 배포하므로, 검증된 코드만 여기로 병합한다

## 브랜치 생성 규칙

```
타입/이슈번호-요약
```

- **타입**: `feat`, `fix`, `docs`, `chore`, `refactor`, `test` 중 이 브랜치의 작업 성격과 가장 가까운 것
- **이슈번호**: 이 작업에 대응하는 GitHub 이슈 번호
- **요약**: 영문, kebab-case (소문자 + 하이픈). 한글/공백/특수문자 금지 — 터미널·URL·CI 로그에서 깨지거나 파싱 문제를 일으킬 수 있음

**예시**
```
docs/1-docs-strategy
docs/1-md-template
feat/12-post-search
fix/20-sqlite-lock
```

같은 이슈를 여러 갈래(설계/구현, 또는 서로 무관한 하위 작업)로 나눠 작업해야 할 때는, 이슈 번호는 같게 두고 요약만 다르게 지어 여러 브랜치를 만들 수 있다 (`docs/1-docs-strategy`, `docs/1-md-template`처럼).

## 병합 규칙

- **직접 push 금지**: `develop`, `main`에는 직접 push하지 않는다 — 반드시 PR을 통해서만 병합한다
- PR은 `ci.yml`(typecheck + 단위 테스트 + E2E)을 통과해야 병합 가능하다
- `develop` → `main`으로의 병합은 실제 배포를 트리거하므로, 이 PR만큼은 병합 전에 변경 사항을 한 번 더 사람이 직접 확인한다

## 브랜치 정리

- PR이 병합되면 그 작업 브랜치는 삭제한다 (오래된 브랜치가 계속 쌓이는 걸 방지)
